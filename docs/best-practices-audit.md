# Best-practices checklist and audit

Written 2026-10-14. This checks Anvil UI against the practices that published, well-known design
systems share: Polaris (Shopify), Carbon (IBM), Atlassian, Primer (GitHub), Spectrum (Adobe), GOV.UK, the
W3C Design Tokens format, WCAG 2.2, and the Radix / shadcn model Anvil builds on. It is drawn from those
systems' public guidance and from the repository as it stands today; I did not re-check their sites live.
Every row below was checked against the repo (files, scripts, configs, counts), not assumed.

Legend: ✅ done · 🟡 partly · ❌ missing · ⏸ deferred on purpose (local-only scope, see `CLAUDE.md`).

## Result

| | Items |
| --- | --- |
| ✅ Done | 35 |
| 🟡 Partly | 13 |
| ❌ Missing | 20 |
| ⏸ Deferred by decision | 8 |
| **Total** | **76** |

Of the 68 items that apply today, **35 (51%) are fully in place** and another 13 are partly there.

**The short version.** The design-and-build half is strong and in places ahead of many public systems:
tokens straight from Figma, a written API contract, accessible primitives, a levelled taxonomy enforced by lint,
usage guidance on every component, axe on every story in two themes, and state coverage (loading, empty,
error) on the data widgets. The gaps are almost all in the **operate** half: no CI, no visual regression, one
browser, no human screen-reader testing, no forced-colors or RTL, and no change-management files
(changelog, contributing, templates). None of them is hard; several are cheap and high-value.

## Checklist and findings

### 1. Foundations and tokens

Tokens are the contract between design and code, and the first thing top systems (Polaris, Carbon, Atlassian, Primer, Spectrum) get right.

| | Practice | Where Anvil is |
| --- | --- | --- |
| ✅ | Tokens live in one machine-readable source (W3C DTCG) | `tokens/anvil.tokens.json`, pulled from Figma variables, styles and text styles; Style Dictionary 5 builds CSS. |
| 🟡 | Tiered tokens: primitive → semantic → component | Primitives (`primitives.css`) feed semantic tokens (`--primary`, `--agent-*`); a few component tokens exist (`--button-*`, `--shell-*`). No formal component tier. |
| ✅ | Semantic names, not raw values, in components | No hex or px literals in components; ESLint and the contract enforce utilities. Theme reset removes Tailwind's default palette. |
| ✅ | Light and dark themes from the same tokens | `:root` / `.dark`; every story is tested in both. |
| 🟡 | Responsive and density modes in tokens | Desktop / mobile modes for dimensions and type; `density` only on Table. No global density setting. |
| ❌ | Multi-brand theming (swap a brand without editing components) | One brand. Radii derive from `--radius`, but there is no documented brand-override layer. |
| ✅ | Motion tokens and reduced-motion policy | Durations and easings as tokens, `docs/motion-foundations.md`, a lint check (`check-motion.mjs`), global reduced-motion handling. |
| ✅ | Generated token documentation | `stories/foundations/*.mdx` are generated by `pnpm tokens:build`. |
| 🟡 | Token build fails on drift | calc() code syntax is checked against Figma on every build; nothing runs it automatically (no CI). |
| ❌ | Contrast pairs verified at token level (an AA matrix) | Contrast is checked per story by axe, and fixes are one-offs (for example the inverse button and disabled text). No token-pair matrix. |

### 2. Component API and architecture

Consistent, predictable APIs are what let teams learn once and reuse everywhere.

| | Practice | Where Anvil is |
| --- | --- | --- |
| ✅ | Written API vocabulary (variant, intent, tone, size…) | `docs/api-contract.md`; the contract wins over Figma. |
| ✅ | Accessible headless primitives underneath | shadcn on Radix keeps focus, keyboard, dismissal and animation behaviour. |
| ✅ | Composition over configuration; slots and `asChild` | Compound parts (Card, Item, Shell, Field); Agent Builder pieces are composed, not re-drawn. |
| ✅ | Controlled and uncontrolled state both supported | `value` / `defaultValue` / `onValueChange` pattern across Stepper, Slot List, Quantity Selector, Media Gallery and others. |
| ✅ | Strict TypeScript, typed public props | TypeScript 6 strict; props are typed and exported per file. |
| ✅ | Component taxonomy enforced by tooling | atom < molecule < organism < agent-builder; `check-stories.mjs` forbids importing a higher level and enforces titles, tags and guides. |
| 🟡 | Reuse and no-duplicates enforced | The rule is in CLAUDE.md and reviewed by hand; levels are linted. Raw `<button>` and `<textarea>` in components are caught by review only. |
| ❌ | Deprecation and breaking-change policy | None. Fine while one team consumes it; needed before anyone else does. |
| ⏸ | Public entry point and package exports | Local development only by decision; there is no `index.ts` and no build for distribution. |

### 3. Accessibility

Top systems treat accessibility as a release gate, not a review comment (Carbon, Spectrum, GOV.UK).

| | Practice | Where Anvil is |
| --- | --- | --- |
| ✅ | Automated axe on every story, both themes | `a11y: { test: 'error' }`; ~1,960 tests run in light and dark. |
| 🟡 | Keyboard and focus behaviour tested | ~370 interaction tests include focus return, arrow keys, Escape and dialogs. Not every component has one (Shell and Shortcut Hint only got theirs recently). |
| ✅ | One consistent visible focus style | `focus-ring` utility; field strokes use `--stroke-focus`. |
| ✅ | Reflow and 320px width | `pnpm audit:narrow` checks every story at 390px; Agent Builder overflow went from 119 stories to 16 (intended scrollers). |
| ✅ | Reduced motion respected | Global; movement becomes a short fade. |
| ✅ | Accessibility guidance per component | Every story has `guide.a11y`; lint requires it. |
| ❌ | Real screen reader testing (VoiceOver, NVDA, JAWS) | Only automated tooling. axe finds roughly a third of issues; live-region and focus-order problems need a human pass. |
| ❌ | Forced-colors / high-contrast mode | No `forced-colors` styles or tests; inset-ring and shadow-based strokes can vanish in Windows High Contrast. |
| 🟡 | Target size (WCAG 2.2: 24px minimum, 44px on touch) | Rating targets were raised to 24px; many controls are 24–32px. No touch-size audit. |
| ❌ | ESLint accessibility rules (`jsx-a11y`) | Not installed; static mistakes (missing labels, click handlers on divs) are only caught at story time. |
| ❌ | Right-to-left support | Two `rtl:` tweaks in Calendar; no RTL toolbar, stories or tests. Logical properties are used in places (`ps-`, `ms-`), not everywhere. |
| 🟡 | Internationalisation (locale, text expansion, plurals) | Strings are props everywhere. `Intl.NumberFormat('en-US')` is hard-coded in Quantity Selector and dates use `date-fns` defaults. No pseudo-localisation story. |

### 5. Quality and testing

Top systems gate every change with automated checks.

| | Practice | Where Anvil is |
| --- | --- | --- |
| ✅ | Interaction tests per component | `Story.test`, run by Vitest browser mode. |
| ✅ | Custom lint for the system's own rules | Story standards, motion rules, levels, `show…`/Full stories. |
| ❌ | Type, lint, test and build run on every change | There is no CI. Everything runs on a laptop, so it depends on remembering to run it. |
| ❌ | Visual regression testing | None. Looks are compared by eye against Figma. Vitest browser mode can take screenshots without a new service. |
| ❌ | Cross-browser coverage | Chromium only (Playwright). Firefox and WebKit matter for focus, `:has()`, container queries and Safari date inputs. |
| ❌ | Unit tests for logic outside components | None; `lib/motion.ts`, the Showroom engine and Stepper maths are only covered through stories. |
| 🟡 | Dependency audit and automated updates | `pnpm audit --prod` is clean. No Dependabot or Renovate; versions are pinned by hand. |
| ❌ | Performance and bundle budgets | No bundle-size or render checks; matters once components are consumed. |
| ❌ | Test coverage reporting | No coverage numbers. |
| ⏸ | Server rendering safety | Vite SPA; no SSR or hydration checks. Needed if consumers use Next.js. |

## What to do about the gaps, in order

Ordered by value for effort. None of these breaks the "local development only" rule; the last group is the
only one that needs a decision.

**Do now (small, high value)**
1. **CI for the checks that already exist.** A workflow running `pnpm typecheck`, `pnpm lint`, `pnpm test-storybook`
   and `pnpm build-storybook` on every PR. It does not host anything. This is the single biggest gap: every
   other guarantee in this table currently depends on someone remembering to run it.
2. **Contribution files.** CONTRIBUTING.md (the human version of CLAUDE.md), a PR template with the
   per-component checklist, CODEOWNERS and an issue template.
3. **`eslint-plugin-jsx-a11y`.** Catches static accessibility mistakes at the keyboard, before a story runs. Needs your
   approval as a new dev dependency.
4. **Dependabot or Renovate**, grouped weekly, so pinned versions do not rot.
5. **Decide the source-of-truth rule in writing:** where code is ahead of Figma, code wins and Figma gets a flag.

**Do next (medium)**
6. **Forced-colors and RTL pass.** Add a `forced-colors` check for focus and strokes, an RTL toolbar toggle, and
   fix physical properties (`left-*`, `pl-*`) to logical ones. Test the 10 most interactive components.
7. **Visual regression.** Vitest browser mode can take screenshots; start with the foundations pages and the
   10 most-used components in light and dark. Pairs with the Figma parity measurement already planned.
8. **Firefox and WebKit** as extra Vitest browser projects (CI only if run time allows).
9. **A human screen-reader pass** (VoiceOver + one Windows reader) on Dialog, Command Palette, Combobox, Calendar,
   Chat Shell, Prompt Input, Message Actions and Approval Card; log findings in the status doc.
10. **Locale pass:** a `locale` and `currency` prop (or a provider) instead of the hard-coded `en-US`, and a
    pseudo-localisation story (long strings) to test text expansion.
11. **Unit tests** for `lib/motion.ts` and the Showroom engine's scheduling and abort behaviour.

**Do before anyone else consumes it (needs a decision from you)**
12. Public entry point and package build (tree-shakeable ES modules with types), changesets, semantic
    versioning, a deprecation policy and changelog, LICENSE.
13. A component-token tier and a brand-override layer if more than one brand is ever needed.
14. Hosted, versioned docs; bundle-size budgets; SSR check (Next.js consumers).
